Part 1 of 2 — Security Fix

Webhook Signature Verification: Fail-Closed

1.1 What is a webhook?

A webhook is an HTTP callback. When an email provider (for example, SendGrid or Mailgun) delivers or bounces an email, it sends a webhook request to the notification engine. The engine uses this request to update the delivery record.

Webhook requests arrive from external providers. The engine must verify that each request comes from the correct provider. It does this by checking a signature. A signature is a cryptographic value that only the real provider can produce.

1.2 What was wrong before the fix?

Problem

The original code used a fail-open pattern. When verification was not possible, the code treated the webhook as verified. Unverified webhooks changed delivery records.

The problem occurred in three situations:

SituationExpected behaviorActual behavior (before fix)
Signature is invalid (wrong key or tampered body)Reject with 401Accept and process
Signature is missing from the requestReject with 401Accept and process
Provider does not support signature verificationReject with 400Accept and process

In the original code, BaseHandler.verifySignature() returned a trusted result even when it could not verify the signature. The code did not have a fail-closed path for unsupported providers.

1.3 What was the impact?

This was a trust boundary violation. The notification engine accepted data from untrusted sources. An attacker did not need to access any internal system. The attacker only needed to send an HTTP request to the public webhook endpoint.

Campus scenario

An attacker sends a forged webhook request that claims all 30,000 exam-change emails were delivered. The engine marks them all as delivered. No retry occurs. Students do not receive the notifications. No operator detects the problem because the records show success.

1.4 How was it fixed?

The fix replaces the fail-open pattern with a fail-closed pattern. The system defines five verification outcomes. Only one outcome allows the system to process a webhook event.

Inbound webhook request arrives at POST /webhooks/:provider
↓
System calls webhooks.verify(provider, {rawBody, headers, body})
↓ Returns one of five outcomes
valid
Signature correct → apply event, return 200
invalid
Signature present but wrong → reject 401
missing
No signature in request → reject 401
unsupported
No verifier for this provider → reject 400
unconfigured
Secret not set by operator → reject 400

There is one exception. An operator can explicitly allow an unsupported provider by setting WEBHOOK_ALLOW_UNVERIFIED_<PROVIDER>=true. In this case, the engine records the webhook as unverified and returns 202. The engine does not apply the event to any delivery record. The applied count is always 0 for unverified requests.

Two verification schemes

The fix implements two cryptographic verification schemes. Each scheme serves a different provider type.

Scheme nameHow it worksProviders
hmac-sha256-body Reads the x-webhook-signature header. Computes HMAC-SHA256 of the raw request body. Uses timingSafeEqual to compare the two values. Generic (custom providers)
timestamp-token Reads a signature object from the request body. Checks that the timestamp is within the allowed window. Computes HMAC-SHA256 of timestamp + token. Mailgun

SendGrid uses ECDSA signatures. The fix does not implement an ECDSA verifier. SendGrid webhooks therefore return the unsupported outcome and are rejected. This is correct fail-closed behavior.

Audit trail

The engine records every webhook request in the webhook_events table. Each row contains the provider name, the verification outcome, whether the event was applied, and a SHA-256 hash of the request body. The row does not contain the signature value or the secret key. This prevents secret leakage through the audit log.

Part 2 of 2 — New Feature

Intelligent Focus Mode

2.1 What is the unique point?

The notification engine already has a digest feature. A digest collects several messages into one email. It groups messages. It does not filter them. It does not classify them by urgency. It does not suppress messages that carry the same underlying fact.

The unique point

Intelligent Focus Mode lets a student hold all non-critical notifications for a set period. It delivers critical events immediately. When the period ends, it sends one summary that shows only the meaningful changes. It suppresses messages that repeat a fact the student already saw.

This is different from a digest in three ways:

  • A digest batches messages by time window. Focus Mode batches messages by student intent (the student chooses to focus).
  • A digest lists every message. Focus Mode correlates related events and shows one item per underlying change.
  • A digest does not bypass critical events. Focus Mode delivers critical events immediately, even during the focus period.

A search of the original codebase found no evidence of Focus Mode, event correlation, acknowledgement-aware suppression, or catch-up summaries. This feature is entirely new.

2.2 What was missing before?

The campus scenario requires that a student receive exam-related notifications reliably but without constant interruption. The original engine had no mechanism to support this. The only options were:

  • Receive all notifications immediately. This causes many interruptions during study periods.
  • Use digest. This delays all notifications, including critical ones such as a room change 15 minutes before an exam.
  • Mute a channel. This blocks all notifications on that channel, with no critical bypass.

None of these options allowed the student to focus and still receive urgent alerts.

2.3 How does it work?

Lifecycle

The student calls POST /inbox/focus-mode/start with a duration (for example, "2h" or 90 minutes). The engine records a focus session for that subscriber. The session has a start time and an end time.

When the end time passes, the engine closes the session automatically. The student can also call POST /inbox/focus-mode/end to close the session early. Either action triggers summary generation.

Event classification

When an event arrives for a subscriber who has an active focus session, the engine classifies the event. The engine uses the workflow definition and the event payload to make this decision.

ClassificationConditionAction
CriticalWorkflow has critical: true, or the event payload matches a criticalRules condition (for example, minutesUntilExam < 30), or the trigger has priority: "critical"Deliver immediately. Bypass Focus Mode. Log focus_bypassed.
Non-criticalAll other eventsHold the event. Set job status to deferred. Set notification status to held. Log step_deferred.

Event correlation

When Focus Mode ends, the engine groups held events by their correlation key. The correlation key is set in the workflow definition (for example, correlationKey: "exam"). Events with the same key and the same correlation value (for example, the same exam identifier) form one group.

Within each group, the engine computes the changes. It compares the first event payload to the last event payload and records which fields changed. Exact duplicate events (same payload as a previous event in the group) increment the suppressed.duplicates counter.

Acknowledgement-aware suppression

If the student already saw a critical bypass event during the focus period, the engine checks whether the held events in the same group carry new information. If the held events do not carry new information (they repeat the same fact as the acknowledged critical event), the engine suppresses them from the summary.

If all held events are suppressed, the engine sets summary.sent = false and does not send a summary message. This avoids a notification with no new content.

Summary generation

The catch-up summary contains one item per correlation group. Each item shows the label, the number of related events, the computed changes, and whether the group was already interrupted by a critical bypass. The summary also lists the suppression counts.

The summary is delivered according to the student's channel preferences. If the student has muted email, the summary arrives as an in-app message only.

Example scenario

TimeEventClassificationAction
3:05 PMExam CS101 — room changed to H123Non-criticalHold

The student receives 2 emails and 2 in-app messages total. Without Focus Mode, the student would receive 4 emails and 4 in-app messages, with no classification by urgency.
